# 开发方式推行方案：Spec 驱动的文档 + 决策留痕 + 机械化门禁

> 本文是从 DeepSeek Harness 的开发方法论中提炼、并针对**中等团队（5-20 人）后端服务（Java/Go/Python，HTTP/RPC）**裁剪后的推行方案。
>
> 核心立场：**不照搬，只移植「骨架 + 灵魂」，砍掉「重装备」。**

---

## 一、为什么值得做（说服理由）

### 1.1 我们正面临的问题（对号入座）

推行前先对照团队是否已有以下痛点，有则方案更容易被接受：

- [ ] 「这个函数当初为什么这么设计？」——没人答得上来，只能去翻 git blame
- [ ] 同一个架构决策被反复争论（比如「为什么选消息队列 A 而不是 B」）
- [ ] 文档和代码脱节：README 写着 A，代码已经是 B
- [ ] 新人/新 agent 上手慢，靠口头传承，没有权威入口
- [ ] code review 靠人肉提醒规范，同样的 review 意见反复出现

**如果勾选 3 项以上，这套方案收益明确。**

### 1.2 这套方法解决什么

DeepSeek Harness 的方法论本质是三件事：

1. **文档分层**：每个事实只有一个家（one home per fact），其余地方只放链接。避免「同一件事在三个地方写、三处都过时」。
2. **决策留痕**：每个非平凡的架构决策都记录「为什么 + 放弃了什么」，防止反复争论。
3. **规范机械化**：能写进 CI 门禁的规则，就不靠人肉 review 口头提醒。

### 1.3 为什么现在适合我们（中等团队）

- 团队 5-20 人：单人口头同步已失效，但还没大到需要重流程，正是引入「轻量结构化」的最佳窗口。
- 后端服务：接口契约、数据格式、存储 schema 是「决策密集」地带，最适合决策留痕。
- 已有一定规模：历史包袱已经出现「为什么当初这么设计」的真空。

## 二、落地原则：裁剪移植

**核心原则：移植骨架和灵魂，砍掉重装备。**

| DeepSeek Harness 机制 | 我们是否采用 | 说明 |
|---|---|---|
| 根 `AGENTS.md`（约定文件） | ✅ 采用 | 改成「人 + AI 共读」的约定文件 |
| 文档分层（one home per fact） | ✅ 采用（精简） | 8 层砍到 3-4 层 |
| Agent Notes（决策记录） | ✅ 采用（精简） | 保留灵魂，简化格式和生命周期 |
| 机械化门禁（verify-*） | ⚠️ 部分采用 | 只保留 2-3 个关键门禁 |
| 双语文档配对 | ❌ 不采用 | 无双语需求 |
| 100% 行覆盖率门禁 | ❌ 不采用 | 改用「关键路径 + 变更行」覆盖 |
| 分层测试（snapshot/web e2e） | ❌ 不采用 | 前端专用，后端不适用 |

## 三、分阶段落地步骤

> 每阶段都有**可验收产出**，避免「只开会不动手」。

### 阶段 0：达成共识（1 周）

**目标**：让核心成员理解「为什么做」，而非「怎么做」。

- 组织一次 30-60 分钟分享，讲清三个痛点（见 1.1）和三个方案（见 1.2）
- 找 1-2 个「决策留痕」的真实例子：挑一个最近反复争论过的架构决策，演示「如果当初有 Agent Note，争论会如何结束」
- **验收产出**：团队同意试点，指定 1 名 owner 负责推进

### 阶段 1：建立文档骨架（1-2 周）

**目标**：搭好「每个事实只有一个家」的分层结构。

后端服务建议的 4 层（而非 DeepSeek 的 8 层）：

```
/
├── AGENTS.md           # 团队约定（人 + AI 共读），1-3 行一条，链接到详细文档
├── docs/
│   ├── architecture.md  # 架构地图：模块、依赖、核心数据流、扩展点
│   └── decisions/       # 决策记录（Agent Notes 的简化版）
├── 各模块 README.md     # 模块契约：接口、配置、语义、限制
└── .github/workflows/   # 门禁脚本（阶段 3 引入）
```

- **验收产出**：`architecture.md` 写完；核心 3-5 个模块的 README 补全；确定「哪些事实该放哪层」的规则

### 阶段 2：引入决策记录（决策留痕，2-4 周试点）

**目标**：让「决策留痕」成为习惯，但**先简化**。

**简化版 Agent Note 格式**（砍掉生命周期状态机，只保留核心）：

```markdown
# 决策：<标题>

日期：YYYY-MM-DD
状态：已实施 | 已否决

## 背景（Problem）
为什么需要做这个决定（不依赖解决方案也能成立）

## 决定（Decision）
用现在时描述实际采用的做法

## 备选方案（Alternatives）
- 方案 A：... —— 否决原因：...
- 方案 B：... —— 否决原因：...

## 影响（Consequences）
代价和收益
```

**试点策略**：先只对「架构级决策」强制要求（比如：新增模块、更换存储、协议变更），不要一开始就覆盖所有改动。

- **验收产出**：积累 5-10 份决策记录；团队形成「写决策记录」的肌肉记忆

### 阶段 3：机械化门禁（持续，按需引入）

**目标**：把最关键的规则变成 CI 脚本，防止文档漂移。

**只引入 2-3 个高价值门禁**（后端适配）：

| 门禁 | 作用 | 后端实现 |
|---|---|---|
| 文档链接校验 | 拒绝死链/坏锚点 | 现成工具（如 markdown-link-check） |
| 契约文档同步 | 接口定义变更时校验文档同步 | 视框架而定（如 OpenAPI 规范 diff） |
| 提交信息规范 | 约定式提交（conventional commits） | 现成工具（如 commitlint） |

**暂缓引入**（避免过度工程）：
- `verify-type-equiv`（类型逐字一致）——后端类型分散在多个语言，成本高
- `verify-doc-budgets`（文档字数预算）——团队规模还没到需要
- 100% 行覆盖率——改用「变更行覆盖」

- **验收产出**：至少 1 个门禁在 CI 上运行，且团队已习惯「CI 红 = 要补文档」

### 阶段 4：复盘与固化（持续）

**目标**：根据试点反馈调整，形成团队自己的版本。

- 每月回顾：哪些规则有效、哪些是负担
- 固化到 `AGENTS.md`，并让它随项目演进

- **验收产出**：一份「本团队开发约定」的稳定版本

## 四、风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| **过度工程化** | 为了写文档而写文档，小改动也要求决策记录 | 明确豁免边界：纯机械/局部编辑不需要；只对「决策面变更」强制 |
| **文档漂移** | 文档写了但没人维护，逐渐和代码脱节 | 阶段 3 的门禁是关键；但门禁引入前靠 owner 巡检 |
| **推行阻力** | 团队觉得「写文档浪费时间」 | 用 1.1 的真实痛点说服；先试点、看收益、再扩大 |
| **门槛过高** | 规则太多，新人/新 agent 记不住 | 根 `AGENTS.md` 保持 1-3 行一条；详细规则链接出去 |
| **形式主义** | 决策记录变成「走过场」，没有真实思考 | `Alternatives` 是强制项——不写被否决方案就拒绝合并 |
| **门禁误伤** | CI 门禁太严，正常改动被卡 | 门禁只校验「硬事实」（死链、格式），不校验「软判断」 |

---

## 五、一句话总结

> 我们不是照搬 DeepSeek Harness 的文档体系，而是学习它「**让规范被机械执行，让决策被留痕，让文档和代码同生命周期**」的工程哲学，并在 5-20 人后端团队的规模下，用最小成本落地。
