## 开场：谜题（5 分钟）

大家好。今天讲一个开源项目，DeepSeek Harness。先抛一个现象。

【停顿】

这个项目从今年六月中旬密集开工，到八月十三号开源，**大约两个月**。两个月里，一个小团队——核心贡献者八个人左右——留下了这样的产出：

- **TypeScript 五十六万行**，其中一半是测试；
- **Markdown 文档十七万行**，和代码同量级；
- **一万多个 commit**；
- 还有一套完整的 CI、文档同步、决策记录体系。

靠什么做到的？

【停顿，让数字停留两秒】

先说三个背景，校准一下预期，免得方向跑偏。

第一，**它确实是重度 agent-first 开发**。开源当天就有人指出，这个项目是"heavily agent-first coded"——大量代码是 AI 写的，仓库里有一整个文件夹，专门放 agent 留下的决策记录。而且这个项目自己是自己的第一个用户，他们用它开发它自己。

第二，**这个团队有很强的系统工程背景**。负责人来自 Jane Street，做量化交易系统的。量化系统那套思维——高可靠、可追踪、可回放——被原封不动带进了这个代码库。

第三，也是最重要的一点：**官方从来没有发过一篇“我们如何用 AI 写了这个项目”的复盘**。没有 retrospective，没有博客。所以今天讲的所有东西，不是他们宣称的，而是我从仓库本身挖出来的——每一个结论都有文件路径，可以现场核对。

关于数字，一句话说死：**commit 数不是产出的尺子**。万级提交里有格式化、有文档同步、有 agent 的自动提交。我们看数字只是为了确认量级——小团队、短周期、极高的迭代密度，这成立。

那答案是什么？

答案不在“AI 有多强”。今天我要讲的是：**答案在研发流程的纪律**。这套纪律可以拆成七层，每一层都可以被机器验证——不存在靠自觉的环节。这是它和“玄学 AGENTS.md”的本质区别。

## 先堵住两个必问的问题（6 分钟）

按惯例，我先把大家最想问的两个问题堵掉，不然讲到一半一定会有人忍不住。

### 问题一：写代码之前，先写 spec 吗？

听众里有人的流程是“先写 spec 再动手”。那我请问：这个仓库的 spec 在哪？

答案是：**在 Issue 模板里，而且是 CI 强制的**。

这个仓库禁用了空白 Issue——你想开个 Issue，必须从五类里选一个：Feature、Bug、Task、Research、Idea。我只念 Feature 这一类的必填项，大家感受一下：

**验收条件、用户或模型可见变化、测试证据。**

注意第三样——**测试证据**。提需求的那一刻，你就得说清楚“怎么证明做对了”。不是写完代码再想怎么测，是提需求的时候就想。

连“调研”这种最容易糊弄的工作，Research 类都要求你预先声明**证据标准**——什么样的证据才算得出了结论。

而且这不是“模板建议”，是机器强制的。仓库里有一个七百行的 policy 脚本挂在 CI 上，Issue 不合规、PR 没引用 Issue，直接挂掉。比如它的报错原文就有这一条：【可以念，就一句】“**PR 正文必须引用至少一个同仓库 Issue**”。

所以“无 Issue 不 PR”是机器拦的，不是口头约定。

再重一点的设计，还有一份专门的文件夹放设计提案，二十五份，每份的骨架就是标准的 RFC：问题、提案、**验收标准**、风险。落地之后转成决策记录——这个第三站细讲。

### 问题二：质量怎么保证？难道在 prompt 里求 AI 写好点？

这是今天最重要的一个观点，我先说出来，后面每一层都在给它提供证据：

**他们不靠提示词让 AI 写好代码，而是让写不好的代码过不去。**

举一个例子就够：这个仓库的 CI 有一个覆盖率门禁，**逐文件 100%**——不是整体 80%，是每一个源文件都要 100%。跑不到，代码进不了主干。

这一条，比一百句“请写高质量代码”都管用。因为它把“质量”从一个形容词，变成了 CI 上的一个布尔值。

还有克隆检测——AI 最爱复制粘贴，这个仓库有跨文件的克隆检测，复制粘贴直接红。

好，两个问题堵住了。现在进正题。

## 总纲：一张图（2 分钟）

整套体系是一张六层的链，外加一块：

```
AGENTS.md → skills → notes → scripts → 执行时机 → code review
(规则是什么)(怎么干) (为什么)  (机器查什么)(何时强制跑)(只查语义)
```

从左到右：规则放在哪、活怎么干、决策为什么这么定、机器怎么查、什么时候强制跑、最后人看什么。

**贯穿全图只有一句话，请大家记住它**：

> 前面各层的全部意义，是把最后那个环节——code review——的负担，压到少量 reviewer 扛得住的程度。

还有一个细节，图上没画出来但很重要：**review 发现的问题会回流**。凡是机器本来可以查、却被 review 抓到的，就补成一个新的门禁脚本。所以这套体系会自己长大、自己变严——项目越大，review 反而越轻。

下面一站一站讲。

## 第一站：AGENTS.md——规则是什么（4 分钟）

AGENTS.md 大家都熟，就是每次会话自动加载的仓库说明。这个仓库的那份，有几个数字：

**1929 个词，31 条规则，上限 1950。**

也就是说，**只剩 21 个词的余量**。想加一条新规则？必须先删一条旧的。

为什么这么苛刻？因为规则文档有个天敌：**只增不减**。每次踩坑都想加一条，三个月后它就长到 AI 吸收不了，规则沦为摆设。预算门禁让“加规则”这个动作有了代价——你得先想清楚什么可以删，也就是**每次都重新排序“什么最重要”**。

更狠的是那个词数上限的调整规则，他们管它叫**棘轮**。棘轮是什么？就是扎带——齿只能往前滑，松不回去。这里指：**上限只许降，不许悄悄升**。想升可以，必须在 PR 里写明理由、接受 review。

所以这份文件永远不会漂移失效，只会越勒越紧。

效果是什么？因为“不知道仓库规矩”而犯的错，在写代码那一刻就消失了。注意这个定位：它是**源头**——后面几层是拦截，这层是让一部分错根本不发生。

## 第二站：skills——活怎么干（4 分钟）

AGENTS.md 有 1950 词的硬上限，那“复杂任务具体怎么一步步做”装得下吗？装不下。

所以第二层：`.agents/skills/` 目录，十一份操作手册，正文合计**一万三千多词**——是 AGENTS.md 的七倍。

关键问题来了：**七倍体量，却没有任何词数预算**。为什么？

这就是这一站最能打的设计——**两级 context 预算**：

- AGENTS.md 是**常驻**的，每次会话都全文进 context，所以必须严格限额；
- skills 是**按需**的——会话开始时进入 context 的只有十一份的目录（名字加一行描述，几百个词），**正文一份都不进**。模型判断当前任务需要哪份，才把哪份读进来。

所以“规则必须极简”和“流程必须极详”这对矛盾，被拆到了两层，各自都不用妥协。

代价全压在那行描述上——它写不准，模型该用的时候不用、不该用的时候乱用。所以这十一份描述**全部以“Use when”开头，写触发条件而不是功能介绍**。比如清理思维链泄漏的那份，描述里直接把要抓的特征字符串列出来——模型看到文档里出现 "no longer" 这种词，就该想起它。

十一份手册里有一份我要单独讲三十秒，因为它最戳人：**push 之前选验证集**。它的核心规则就一句话——**按改动面选最小的验证集，禁止默认全量跑**。改了文档就跑文档同步，改了模型输出就跑快照，真实 API 才跑 e2e。而且两头都堵：既禁止“一改就跑全套”，也禁止“跑不过就把阈值调低”——降覆盖率、加 `--passWithNoTests`，全被点名禁止。

【看听众】在座各位都受过“改一行代码跑半小时全套测试”的苦吧。这一份手册，治的就是这个病。

## 插播：cookbook——这类代码怎么写（3 分钟）

顺着 skills 再讲一小块，因为它俩容易被混为一谈。

`.agents/skills/` 是“元操作手册”——怎么做 review、怎么选验证集。但“我要加一个工具、加一个包，第一步干什么”这种事，在另一个地方：`docs/cookbook/`，九份手册，近一万词。

两者怎么分？一句话：**skills 管怎么做事，cookbook 管怎么写这类代码**。

cookbook 里有一条特别值得抄的模式。AGENTS.md 的 31 条规则里有这么一条，我念一下大意：

> 工具的 UI 渲染意图是设计的一部分，**必须事先决定**。

“事先决定”——spec-first 落到代码层的具体形态。那“怎么事先决定、有哪几种选项、怎么验证”？全在 cookbook 的《加一个工具》里，一千七百词。

也就是说，**同一条知识被切成了三段**：铁律在 AGENTS.md 占一行，操作细节在 cookbook 占一千七百词，设计理由在决策记录里。常驻的极简，按需的极详——和上一站是同一个套路。

还有一条细节我很喜欢：cookbook 里的示例代码，**除了少数标注豁免的，其余全部参与编译检查**。文档里的示例代码在某次重构后悄悄跑不动了、直到有新人照抄——这种事故在这里物理上不会发生。

## 第三站：notes——决策怎么留痕（5 分钟）

前面讲的是“怎么做”。但 agent 干活时会不断做决策——选 A 不选 B，否决某个方案。这些“为什么”和“放弃了什么”，代码装不下。第三站就解决这个。

这个仓库有个文件夹放决策记录，英文叫 Agent Note，本质就是**由 AI 写的 RFC 和 ADR**。实测数量：活跃的五百五十一份，归档的一百四十二份。

每份记录的状态编码在**路径**里：提案、已落地、被否、归档，四个文件夹。状态变了就是移动文件——一个明确的、不会忘的动作。

这一站最有价值的一条规则，也是今天第二个“抄回去就能用”的东西：

**每份记录必须有“考虑过的备选方案”这一节——记录每个被否决的方案和落选原因。**

为什么强制？原话很妙：“**记录决策却不记录它击败了什么，等于邀请反复争论。**”

但真正让我佩服的是配套的那条规则。备选方案补不出来的老记录怎么办？一般团队的做法是让 AI 补一个——AI 完全能编出一段像模像样的“我们考虑过 X，因为 Y 放弃了”。

这个仓库的选择是：**禁止编造**。补不出来的，必须留一个逐字精确的标注注释，意思就是“这里缺着”。实测十九份带着这个诚实的缺口。

为什么宁缺勿编？因为**一旦允许补编，整个决策记录体系的可信度就归零了**——你再也无法区分哪条理由是真的。宁可有个诚实的洞，也不要编造的理由。

再讲三十秒“被否”文件夹，十一份，每一份的判决就一行。我挑两条：

一条是有人提议用 Node 内置的定时器替换手写的 sleep，理由充分、看起来显然该做——**真去实现了，实现完了发现前提不成立**：测试框架的假时钟拦不住它。这个实验结论被保存了下来，而不是随着被关掉的 PR 消失。

另一条干脆叫“依赖替换被否决清单”——一次完整调研的结论，被否的理由逐条写清，末尾一句：记录下来，**免得这份调研从零重跑**。

所以“被否”文件夹不是垃圾桶，是**学费存档**。这些“看起来显然该做”的简化，每一个都会被下一个 agent 重新提出来——AI 没有记忆，它一定会再提。有这一行判决在，reviewer 一句话就能驳回。

## 第四站：scripts——机器查什么（4 分钟）

前三层产出了规则、手册、决策记录——**全是文字**。第四层把文字变成代码。

这一站的立法原则就一句话，念完大家就知道整层是怎么运转的：

> **AGENTS.md 里每一条机器可查的承诺，都必须有一条会返回非零退出码的命令。**

为什么必须这样？他们自己的原话，也是整个仓库最重要的一句自述：

> 这个代码库主要由 coding agent 开发。**agent 遵守强制门禁的可靠性，远高于遵守散文约定。**

注意措辞——不是“AI 不可靠”，而是“门禁比散文可靠得多”。这个差别很关键。AI 的问题不是不听话，而是**它没有“上次被骂过”的记忆**。一条只写在文档里的规则，对它来说是每次会话都要重新赌一次的规则；一条会红的 CI，才是每次都生效的规则。

规模上，一百二十八个脚本，组织成六十个左右的门禁、十三个聚合模式。有一个数字值得单独说：**文档同步这一个聚合，就挂着二十八个门禁，其中二十五个在管文档**。

过半的机器检查在管文字。一个代码仓库为什么这样？因为**AI 是读文档来理解仓库的——文档错了，AI 就系统性 地错**。人读错文档还有“感觉不对，去看看代码”的本能，AI 倾向于信任文档。所以文档的正确性，对 AI 比对人更关键。

最后三十秒讲一个极容易漏的设计。词数预算门禁查三类失败，其中第二类是精髓：**被预算的文件不存在，也算失败**。

为什么这条必须有？因为光查“超字数”的话——**把文件删了，门禁就绿了**。约束被删除这件事本身，消灭了约束。所有清单式的门禁都有这个洞，这一条就是补洞的。

## 第五站：执行时机——什么时候强制跑（4 分钟）

第四站造出了六十个门禁，那哪些在本地跑、哪些在 CI 跑？

直觉答案是“本地尽量多跑，早发现早修”。**这个直觉是错的。**

他们的理由有三条，第三条最关键：本地全量跑完，CI 马上要把同样的东西再跑一遍——**这次本地运行的信息量是零**。这不是“快和严”的取舍，这是重复劳动。

所以边界是：**本地窄而快，CI 全而慢**。配置文件的第一行注释就把这个写死了。

具体到本地：提交前的钩子只有六个检查，全部按改动文件精确触发——改了什么才查什么；能自动修的直接修掉而不是拒绝；**推送前只有一个检查**，类型检查。而提交前明确**不跑**的东西被写成了一份否定清单：不跑类型分析、不跑测试、不跑快照、不跑文档检查、不跑构建——七项，白纸黑字。

为什么要写“不做什么”？因为下一个人看到钩子里没有测试，会本能地想“是不是漏了，我加上吧”。有这份清单在，他知道那是刻意的。

这一站戳人的那句话，大家都懂：**太慢的钩子一定会被绕过**。`--no-verify` 敲一次就再也回不来了，最后形同虚设。所以快不是体验问题，是存亡问题。

CI 那边我只讲一个设计，三十秒，但它可能是今天最能抄走的一条。CI 有一个只做汇总的 job，给分支保护提供稳定的检查名。它的注释里有一句话我原样念：

> **`if: always()` 是承重的**——没有它，依赖失败会跳过这个 job，而 GitHub 把“被跳过的必需检查”算作通过。

拆开看就是：上游全挂 → 汇总被跳过 → 分支保护认为一切正常 → **可以合并**。整个 CI 保护静默失效，一个红色信号都没有。修复只需要三个字符，但前提是你得知道这个洞存在。

## 第六站：code review——最后一道防线（6 分钟）

前面各层把事实类问题清零了，但总有机器物理上查不了的东西——“这个抽象有没有存在的必要”“这个测试是不是在复述实现”。最后一道防线就是 review。

这一站必然被挑战，我把挑战和我一起说。

**挑战：这么大产出，人工 review 扛得住吗？**

扛不住。所以**根本不靠人扛**。review 的标准本身是一份 skill——就是第二站讲的那种、写给 AI 执行的手册。一千零七十三个词，装了六条硬阻断、十四项人工检查。所以真实模型是：**AI review AI，人只做仲裁**。产出侧用 agent 扩容，review 侧也用 agent 扩容——**两侧用同一种方式扩容，这才是高吞吐下质量不塌的真正原因**。

**挑战：那是不是全靠测试和 lint 了？**

他们自己否认过，原文四连：覆盖率必要，但不证明场景正确；不要相信 agent 的自我报告；自动检查建立不了文字的准确性；配对哈希绿了不代表翻译是对的。

而且有一份决策记录亲口承认：早期有一批测试本身类型就是错的，测试框架不查类型，**是 review 抓到的**——抓到之后他们才把类型检查补进 CI。这就是“review 的漏网之鱼回流成新门禁”的第一现场，有文件有编号。

review 具体查什么？十四项，我挑两项感受一下：

一项叫**执行路径**：沿着每一条“拒绝”逻辑，找到真正执行操作的地方，然后**主动去找能绕过它的备用调用方**——绕过 schema 的、绕过门面的、利用监听器顺序的。纯语义推理，任何 lint 都做不到。

另一项叫**投机性泛化**：每个抽象、每个配置项，都要能指出“当前的哪个生产消费者在用它”。指不出来，就是为“以后可能需要”而写的——**AI 最爱写这种代码**，每个单看都合理，攒多了就是没人看得懂的库。

最后三条纪律，条条针对 AI 的通病，念完大家自己品：

第一，**一个有据可依的 blocker，好过一堆 nit**。否则 AI reviewer 会用二十条“建议改个变量名”伪装出“很认真”。

第二，**反谄媚条款**，原文我念一下：收到 review，逐条核实，该修就修，**该反驳就用技术理由反驳——不许表演性同意**。这条专治“您说得对，我马上改”然后改得更烂。更深一层：reviewer 自己也可能误判，AI 一味照办，错误就进了代码库。**review 是双向的信息交换，谄媚把它降级成了单向命令。**

第三，来自另一份手册，我认为是全仓库对 AI 协作最清醒的一句话，也是今天最后一个金句：

> 委托出去的修复要信任但验证——**子 agent 的报告描述的是意图，不一定是落地的事实**。回归守卫必须先证明它在未修复的代码上会红——**一个两边都绿的守卫，什么都没守**。而**一个把问题重新表述成“已经处理了”的子 agent，是你要亲自下场查的信号**。

最后这半句太准了。AI 最典型的失败模式不是报错，而是**说服你问题不存在**。

## 收尾：闭环与第一步（4 分钟）

七层讲完了，回收开场那个谜题：两个月、小团队、五十六万行，靠什么？

不是靠模型强。是把纪律做成了**会自我生长的系统**：

规则进 AGENTS.md，有预算有棘轮，不会腐烂；流程进 skills 和 cookbook，按需加载，不占 context；决策进 notes，带着被否决的方案，不会反复争论；每条承诺变成一条会红的命令；本地快、CI 全；review 只查语义、而且 reviewer 本身可以是 AI。

而那条**回边**是灵魂：review 抓到的、机器本来能查的问题，回流成新门禁。所以门禁集合是被 review 喂大的，**项目越大，review 越轻**。

最后给大家迁移的第一步。不用搭七层，**今天就只需要做一件事**：

去你们仓库的 Issue 模板配置里，把一行改成 `blank_issues_enabled: false`，然后立两三个模板，每个必填两个字段：**验收条件、测试证据**。

改一个 YAML 文件的事。但它意味着：从今天起，你们团队每一个需求，从诞生那一刻起就带着“怎么证明做对了”。

这是整套体系里投入产出比最高的一步。剩下的，按需长。

谢谢大家。

# Q&A 弹药（不念，被问到再用）

**Q：这流程里没有 review 吧？**
五张牌：① review 标准是 1073 词的 skill，6 硬阻断 + 14 人工检查，信息密度全仓库最高；② 扛不住所以不靠人扛，AI review AI 人仲裁；③ 他们自己否认“全靠测试”——“覆盖率不证明场景正确”“不要信 agent 的自我报告”；④ 门禁和 review 是减负关系不是替代——原文“门禁绿了的不再提”；⑤ 有一份 note 承认 bug“only caught by a review”，抓到后补了门禁。

**Q：用了 superpowers / SDD 之类方法论吗？**
没有，仓库里搜不到。它把 spec-first 的实质拆进 Issue 模板、proposed note 和 cookbook，然后全部机器强制。不起名字但每条可执行——这反而更好抄。

**Q：只适合他们那种项目吧？**
回边意味着可以从小长起。三个门禁起步，让 review 告诉你下一个补什么。

**Q：没人力写这么多门禁。**
他们原话：“当干活的是 agent 时，‘工作量大’不构成成本理由。”写门禁这件事本身也是 agent 干的活。

**Q：数字可信吗？**
口径都在底稿里：64 天窗口、TS 56.8 万行（测试 30.7 万）、MD 17 万行、活跃 note 551 份。commit 数不是尺子，量级成立即可。
