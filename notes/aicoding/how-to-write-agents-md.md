# 怎么写 AGENTS.md：判定标准与写作方法

> 回答一个常见困惑：在自己项目里写 `AGENTS.md`，该写哪些、不该写哪些、怎么写，如何判断写得对不对。
>
> 核心结论：**这不是玄学，有明确的判定标准和写作方法。且 AGENTS.md 不是「写出来的」，是「长出来的」。**

---

## 一、先破除迷思：AGENTS.md 是「长出来的」，不是「写出来的」

大多数人一开始就想写一份完美的 AGENTS.md，这注定失败，因为：

> 你不可能在还没深度用 AI 之前，就知道该约束 AI 什么。

DeepSeek Harness 的 `AGENTS.md` 是**经过无数次「AI 犯错 → 把教训固化成一条规则」之后长成的**。证据就在文件里——很多规则都链接到带日期的 Agent Note，说明「这条规则是某次真实决策的沉淀」。

**正确的起点**：先写一个极简版（10 行以内），然后在用 AI 的过程中，每踩一次坑就往里加一条。一个月后，AGENTS.md 自然就是「对的」，因为每一条都对应一个真实发生过的坑。

---

## 二、该写什么、不该写什么：唯一判定标准是「可裁定」

判断一条规则该不该进 AGENTS.md，只有一个标准：

> **这条规则，AI 违反后能不能被「机器检查」或「人一眼裁定」发现？**

| 规则 | 能裁定吗 | 该写吗 |
|---|---|---|
| "代码要优雅、要可维护" | ❌ 无法判定 | ❌ 不写 |
| "接口必须用 protobuf 定义，禁止裸 JSON" | ✅ 一眼可查 | ✅ 写 |
| "错误必须返回结构化 code，不能只返回 string" | ✅ 一眼可查 | ✅ 写 |
| "配置项不能硬编码，要走 Config" | ✅ 可 lint/查 | ✅ 写 |
| "要注意性能" | ❌ 无法判定 | ❌ 不写 |
| "DB 变更必须带 migration 脚本" | ✅ 一眼可查 | ✅ 写 |

**为什么「可裁定」是关键？** AGENTS.md 的读者是 AI，AI 需要**明确的是非题**。模糊的形容词（优雅、健壮、高性能）对 AI 来说等于噪声——它既无法遵守，你也无法判断它是否遵守。

DeepSeek Harness 的 33 条 Conventions，**每一条都是可裁定的**（"Switch on discriminant tags"、"Opaque ids are branded"、"Misconfiguration fails loud"），没有一条是形容词堆砌。

## 三、写什么内容：用「四个问题」自检

一份合格的 AGENTS.md，应该让 AI 进入仓库后**不需要猜**就能回答这四个问题：

### 1. 这是什么系统？（世界模型）
- 用 1-3 句话说清系统本质和核心心智模型
- 给出目录/模块地图（每个模块一行职责）
- **反面教材**：写项目背景故事、写愿景

### 2. 哪些地方最危险、改之前要先读什么？（风险前置门）
- 明确「改 X 之前必须先读 Y」
- 明确「哪些地方绝对不能动」
- 明确当前阶段的风险姿态（激进 or 保守）

### 3. 怎么干活？（命令 + 约定）
- 关键命令（不是全部命令，是 AI 会用到的）+ 每个命令的行为预期
- 编码约定（必须是可裁定的）
- 测试约定（改了什么要跑什么）

### 4. 怎么证明做对了？（验证）
- 什么改动配什么验证
- 有哪些门禁会拦我

## 四、怎么写：四个写作技巧（来自 DeepSeek Harness 的实证）

### 技巧 1：每条规则 1-3 行，理由外链

DeepSeek Harness 明确要求「每条规则 1-3 行」「≤1600 词」。因为 AI 的注意力会稀释——塞 50 条规则，等于一条都记不住。

**规则本体留在 AGENTS.md，详细理由链接出去。** 如果某条规则需要 10 行解释「为什么」，那解释放 docs，AGENTS.md 只留一句「规则 + 链接」。

### 技巧 2：每条规则 = 「加粗短语 + 具体约束 + 反例」

看 DeepSeek 的写法：

```
**No hardcoded tunables in plugins**: deployment-varying choices are validated Config fields
```

结构：**一句话原则（加粗）** → 具体怎么执行 → 什么不算数（反例）。

照这个模板写：

```
**禁止硬编码配置**: 环境相关值走 Config；`DEFAULT_*` 常量不算可配置性
```

### 技巧 3：规则要「自包含」，但理由要「单点存放」

一条规则被单独读到时要能懂（自包含），但同一条规则的「为什么」只在**一个地方**详细写（one home per fact）。

### 技巧 4：为「已知的 AI 坏习惯」写针对性条款

DeepSeek 的 AGENTS.md 里有一批条款，每条都精准打击一个 AI 的经典失败模式：
- 防误诊（先排除环境再查代码）
- 防浪费（禁止默认全量跑测试）
- 防作弊（禁止拿沙箱当借口跳过真测试）
- 防空话（禁比喻、禁模糊词）

**这部分是「长出来的」**——你踩了坑才知道要防什么，一开始写不出来。

## 五、最实用的建议：分三步走，而不是一步到位

### 第一步（今天就做）：写一份「骨架版」AGENTS.md（10 行以内）

只写四样东西，够 AI 起步即可：

```markdown
# AGENTS.md

## 系统
<1-3 句话：这是什么系统、核心心智模型>

## 目录
<模块地图：每个模块一行>

## 危险区
<改哪些地方前必须先读什么>

## 命令
<AI 会用到的关键命令 + 行为预期>
```

**注意**：这一版**故意不写 Conventions**（编码规则），因为你现在还不知道要约束 AI 什么。写错了反而有害。

### 第二步（用一周 AI 后）：开始积累 Conventions

每当你 code review AI 的产出时，发现一个「你反复提醒它、它反复犯」的问题，就把它写成一条**可裁定的规则**加进 Conventions。

判断依据：**这条错误如果写进了规则，AI 下次能避免吗？** 能 → 写；不能（还是靠人肉判断）→ 不写。

### 第三步（有 CI 基础后）：把能机械化的规则升级成门禁

当某条 Conventions 被频繁违反，且「违反」可以被脚本检测时，把它从「文字规则」升级成「CI 门禁」。这时才真正进入 DeepSeek Harness 的「Executable Constraints」阶段。

## 六、怎么判断「写得对不对」：一个终极自检

写完后，问自己这一句：

> **如果我是一个第一次进入这个仓库的 AI，读完这份 AGENTS.md，我会不会「照着做错事」？**

- 会照着做错 → 说明有规则写错了/写模糊了，删掉或改精确
- 读完后还是不知道该怎么干活 → 说明缺了关键信息（系统本质/命令/验证）
- 读完后能安全地开始干活，且不会犯「规则里有、但你没写清楚」的错 → 就是对的

**记住一个朴素真理**：写错的规则比没写更糟。所以当你拿不准某条要不要写、怎么写时，**宁可不写，等踩坑了再加**。
